# Промпт: план чтения Telegram-каналов для OneS News

Скопируй весь текст ниже в новый чат с агентом. Цель этого прогона — **только исследование и письменный план**. Код, коммиты и правки `sources.yaml` запрещены, пока человек явно не скажет «реализуй».

---

## Роль

Ты архитектор сборщика OneS News. Твоя задача — разобрать, как надёжно читать **публичные Telegram-каналы, перечисленные в `sources.yaml`**, и писать их посты в `data/days/YYYY-MM-DD.json` **теми же полями**, что уже есть у сайта и RSS.

Ты **не** пишешь код в этом прогоне. Ты **не** «улучшаешь заодно» UI, Infostart или Gemini. Если что-то уже реализовано — это фиксируешь в плане, а не переписываешь молча.

## Жёсткие запреты

- Не создавать и не править `.py`, `.js`, `.html`, `.css`, workflow, `sources.yaml`, `agent/config.yaml`, day-JSON.
- Не предлагать «давайте сразу набросаем Telethon» до сравнения вариантов.
- Не предлагать ИИ ходить в Telegram «как браузер» вместо скрипта.
- Не предлагать неофициальные платные «Telegram scraping API» как основной путь.
- Не утверждать факты про Bot API / MTProto / `t.me/s` по памяти: сначала проверь текущий код репозитория, затем — актуальную документацию Telegram (Bot API, MTProto, web preview).
- Не заканчивать ответ списком «вариантов на выбор» без **одной** рекомендации и обоснования под наш стек (статический сайт + `python agent/run.py` + GitHub Actions).

## Обязательный порядок работы

Выполняй шаги **по порядку**. В финальном ответе должно быть видно, что каждый шаг сделан. Если шаг пропущен — план считается неготовым.

### Шаг 1. Контракт данных (репозиторий)

Прочитай и законспектируй:

- `PROJECT.md` — схема `data/days/*.json`, поля item, `source_type: telegram`, правила саммари, что робот может трогать.
- `sources.yaml` — секция `telegram`: поля `name`, `url`, `home`, `fetch`, `language`, `enabled`, `summarize`.
- `agent/collect.py` — функции `telegram_s_url`, `collect_telegram_web`, ветки `fetch == "telegram_web"` в `collect_source` и `collect_range`.
- `agent/run.py` — как raw-записи доходят до `write_day` / `merge_sources_into_day`, флаги `--skip-llm` и `summarize: false`.
- `agent/write_day.py` — `to_day_item`: какие ключи попадают в day-файл.
- `agent/common.py` — `load_sources`, `SECTION_TO_TYPE`.
- `.github/workflows/collect.yml` — что есть в раннере (секреты, зависимости, push).

Зафиксируй **как есть сегодня**: что уже умеет `collect_telegram_web`, чего не умеет (пагинация, медиа без текста, форварды, дата в TZ, лимит постов на странице).

### Шаг 2. Источник правды по каналам

План обязан исходить из того, что **список каналов живёт в `sources.yaml`**, секция `telegram`, а не в хардкоде и не в отдельном «файле задач» вне репозитория.

Для каждой записи:

- `url` — адрес, который читает сборщик (`https://t.me/s/username` или `https://t.me/username`; скрипт нормализует).
- `home` — публичная страница для `about.html` (`https://t.me/username`).
- `name` → `source_name` в карточке и фильтре.
- `fetch: telegram_web` (или иной код, если план обоснованно меняет fetch-тип).
- `enabled: true` — только такие каналы собираются.
- `summarize: false|true` — см. шаг 5.

Запрещено требовать второй список каналов (Google Sheet, .env, комментарий в чате).

### Шаг 3. Карта полей (обязательная таблица)

Построй таблицу: **поле day-JSON → откуда берём в Telegram-посте → fallback**.

Поля item (менять схему **нельзя** без явной просьбы человека):

| Поле | Ожидание |
|------|----------|
| `id` | `{date}-{nnn}` как сейчас, через `slug_id` |
| `title` | не пустой; без ИИ — эвристика из текста поста |
| `summary` | 2–4 предложения либо очищенный текст поста |
| `url` | каноническая ссылка на пост `https://t.me/username/id` |
| `author` | имя канала / подпись автора поста / «Не указан» |
| `source_name` | `name` из `sources.yaml` |
| `source_type` | всегда `telegram` |
| `topics` | хештеги поста или `[]` |
| `language` | `language` источника |

Отдельно распиши raw-поля до `write_day`: `snippet`, `published_at`, `summarize`.

### Шаг 4. Сравнение способов чтения (обязательная матрица)

Сравни **четыре** пути. По каждому: что читает, нужны ли аккаунт/бот/секреты, история постов, приватные каналы, пригодность для GitHub Actions, хрупкость, соответствие ToS, трудоёмкость.

1. **Публичный HTML-превью** `https://t.me/s/{username}` (то, что уже начато в `collect_telegram_web`).
2. **Bot API** (бот через @BotFather, `getUpdates` / webhook, `channel_post`).
3. **MTProto user API** (Telethon / Pyrogram, `api_id` + `api_hash` + сессия пользователя).
4. **Сторонний RSS-прокси** (RSSHub и аналоги: канал → RSS → уже существующий `collect_rss`).

В матрице **явно ответь на вопросы человека**:

- Можно ли обойтись **без ИИ** на этапе чтения канала?
- Нужен ли **бот** в Telegram?
- Есть ли **официальное API**, которым мы реально можем забрать посты канала по username из yaml?

Ответы должны быть однозначными (да/нет + одно предложение «почему»), не «смотря как».

Ожидаемая рамка (проверь по докам и скорректируй, если устарело):

- **Чтение публичного канала по списку из yaml без вступления бота в канал:** Bot API **не** даёт `getChatHistory`. Бот видит новые `channel_post` только если его добавили в канал (обычно как админа) **после** добавления. Это непригодно как основной способ для произвольных публичных каналов 1С.
- **MTProto** умеет читать публичные каналы от имени пользователя, но это сессия телефона, риск бана, секрет в Actions, интерактивный логин — плохо стыкуется с текущим cron.
- **ИИ не нужен, чтобы скачать и разобрать пост.** ИИ у нас уже есть только как опциональный слой саммари (`summarize: true` → Gemini). Для коротких постов канала достаточно `summarize: false`.
- **Бот не нужен**, если остаёмся на `t.me/s` или (хуже) на RSS-прокси.

После матрицы: **одна** рекомендация для v1 и что отложить в v2. Рекомендация должна учитывать, что заготовка `telegram_web` уже есть.

### Шаг 5. Нужен ли Gemini

Отдельным подразделом:

- Что делает скрипт без модели: заголовок, url, дата, автор, snippet, topics.
- Когда `summarize: false` достаточно (типичный Telegram-пост уже короткий).
- Когда `summarize: true` имеет смысл (длинные посты, несколько тем в одном сообщении).
- Как `--skip-llm` и отсутствие `GEMINI_API_KEY` должны вести себя для telegram-источников.
- Запрет: модель не ходит в Telegram и не выбирает, какие каналы читать.

### Шаг 6. Ограничения `t.me/s` (если рекомендуешь web)

Проверь актуальную вёрстку превью (можно fetch одного публичного канала) и опиши:

- сколько постов на первой странице;
- есть ли пагинация (`?before=` / `data-before` / cursor) и как крутить её **до даты** `--date` / `--from-date`, не выкачивая всю историю;
- посты только с фото/видео без текста;
- репосты / forwarded;
- каналы с выключенным web preview;
- дата/время и TZ (`Europe/Moscow` из `agent/config.yaml`);
- антибот / 429 / пустая страница;
- стабильность CSS-классов (`tgme_widget_message`, `data-post`, `tgme_widget_message_text`, `<time datetime>`).

Если HTML нельзя проверить из среды — честно напиши, что не проверено, и какие проверки обязан сделать человек перед реализацией.

### Шаг 7. Встраивание в текущий пайплайн

План должен описать **минимальный** путь, без нового CLI:

```text
sources.yaml (telegram, enabled: true)
    → collect.py collect_telegram_web (или наследник)
    → agent/tmp/raw-YYYY-MM-DD.json
    → summarize / skip
    → write_day.py → data/days/YYYY-MM-DD.json + data/index.json
```

Расписать:

- однодневный прогон `python agent/run.py --date YYYY-MM-DD`;
- диапазон `--from-date` / `--to-date` (сейчас telegram в `collect_range` крутит цикл по дням с одной HTML-страницы — это дыра, план обязан её назвать и закрыть);
- merge: не затирать Habr/Infostart при дописывании telegram;
- дедуп по `url` поста внутри дня;
- `max_items` и `snippet_chars` из `agent/config.yaml`;
- GitHub Actions: новые секреты **не** нужны, если нет Bot/MTProto; если рекомендация всё же требует секрет — описать какой и почему это хуже.

### Шаг 8. Критерии готовности и риски

Чеклист приёмки (человек сможет проверить без чтения кода):

1. В `sources.yaml` включили канал → после `run.py` в day-JSON появились карточки с `source_type: "telegram"` и тем же `source_name`.
2. Выключили `enabled: false` → канал исчез из следующего сбора (каталог `data/sources.json` тоже).
3. Поля карточки совпадают со схемой §5 `PROJECT.md`.
4. Посты не того календарного дня (MSK) не попадают в файл дня.
5. Повторный прогон того же дня не плодит дубликаты этого канала.
6. Сайт/RSS не сломались.

Риски: смена HTML Telegram, пустой `t.me/s`, только медиа, лимит первой страницы vs диапазон дат, ToS.

## Формат финального ответа

Ответ **на русском**. Структура **строго** такая (заголовки скопируй):

1. **Что уже есть в репозитории** — факты по коду, без воды.
2. **Ответы на три вопроса** — без ИИ? есть API? нужен бот? Каждый: да/нет + почему.
3. **Матрица способов** — таблица 4 путей.
4. **Рекомендация v1 / v2**.
5. **Карта полей** — таблица.
6. **Алгоритм чтения канала** — пошагово, псевдокод допустим, настоящий Python — нет.
7. **Изменения файлов (когда разрешат кодить)** — список файлов и суть правки, без патча.
8. **Проверки перед кодом** — что человек/агент должен увидеть на живом `t.me/s`.
9. **Открытые вопросы человеку** — только если без ответа нельзя реализовать (например: конкретные username каналов). Если в yaml уже есть пример — не спрашивай «а какие каналы?», спроси «какие включить вместо example».

Объём: достаточно подробный, чтобы следующий чат мог реализовать без повторного исследования. Не пиши код. Не обещай реализацию в этом же ответе.

## Критерий «план готов»

План готов только если:

- процитировано, что делает текущий `collect_telegram_web`;
- есть однозначные ответы «без ИИ / API / бот»;
- выбрана одна рекомендация;
- каждое поле day-JSON имеет источник;
- названа дыра диапазона дат для telegram;
- нет патчей и новых исходников.
